# 운영 데이터 전환 로드맵

## 현재 상태

인증·사용자 프로필·온보딩과 화면 데이터의 런타임 원천을 PostgreSQL로 전환했다.
Auth.js v5 Credentials는 `ax_private.auth_users`를 사용하고, 공개 프로필은
`ax_core.profiles`, 온보딩 원문과 동의는 `ax_private.onboarding_profiles`에 저장한다.
사용자별 실행 상태는 `ax_private.user_runtime_states`에 저장되어 새로고침과 재로그인
뒤에도 유지된다.

35개 서비스 데이터셋은 공개 범위에 따라 `ax_core.datasets`와
`ax_private.datasets`에 적재한다. 테스트 파일을 제외한 런타임 코드의 `src/data` 직접
import는 0개이며, 화면은 인증된 서버 API 또는 서버 저장소를 통해 데이터를 읽는다.
현재 들어 있는 레코드의 내용은 심사용 예시 데이터이므로, 운영 전에는 검수된 실데이터로
교체해야 한다.

## 전환 원칙

1. 화면 컴포넌트는 `src/data`를 직접 import하지 않고 서버 API 또는 서버 DAL만 사용한다.
2. 개인정보·동의·매칭 원문·거래 정보는 `ax_private`, 공개 가능한 분류·기관·콘텐츠는
   `ax_core`에 둔다.
3. `public` 스키마에는 서비스 테이블을 만들지 않으며 두 스키마를 Supabase Data API에
   노출하지 않는다.
   일반 데이터 API도 비공개 요구·동의·딜을 인증 사용자의 역할과 persona로 행 단위 제한하고,
   매칭 원문·점수·회원 비공개 원본은 브라우저에 제공하지 않는다.
4. DB 연결 실패 시 JSON 시드로 조용히 대체하지 않는다. 운영 모드에서는 오류를 드러내고
   쓰기를 중단한다.
5. 목업 식별자를 로그인한 사용자 UUID로 바꾸며, 사용자 ID와 역할은 항상 서버 세션에서
   가져온다.
6. `src/data` 원본은 DB 초기 적재와 테스트 픽스처에만 사용하며 애플리케이션 런타임에서는
   참조하지 않는다.

## 단계별 범위

### 1. 인증·프로필·온보딩

- 상태: 마이그레이션·시드·DB 검증 완료
- 테이블: `auth_users`, `profiles`, `onboarding_profiles`, `auth_events`
- 완료 내용: 회원가입, 로그인, 세션 유지, 온보딩 완료 후 DB 영속화 경로 구현

### 2. 기준정보

- 대상: 분야, 태그, VC 단계, 용어 사전, 인터뷰 문항, 거절 사유
- 성격: 여러 화면이 함께 읽는 변경 빈도가 낮은 공개 데이터
- 상태: `ax_core.datasets`와 인증 서버 API로 전환 완료

### 3. 사람·매칭·추천

- 대상: 회원 공개 정보, 비공개 요구·제안, 영향 의도, 동의 영수증, 추천, 매칭 점수
- 주의: 가장 민감한 영역이므로 동의 목적과 공개 범위를 행 단위로 검증한다.
- 상태: 보호 데이터셋, 서버 세션의 persona ID, DB 사용자 상태 기반으로 전환 완료

### 4. 조직·생태계·협업사례

- 대상: 기관, 생태계 관계, 협업사례, 협업관계, 하위 모둠
- 상태: 생태계·협업사례 화면이 동일한 DB 원천과 명시적 오류 상태를 사용

### 5. 기회·자원·진단

- 대상: 기회, 자원, 금융상품, 전문가 서비스, 5 Forces, 갭 카드, 단계 연결
- 상태: 저장된 기준정보와 데이터셋 조회 API로 전환 완료

### 6. 실행 워크플로

- 대상: 딜룸, 밋업, 프로젝트 제안, 리뷰, KPI
- 주의: 생성·수정·상태 변경에는 권한 검사, 감사 이벤트, 낙관적 잠금 또는 revision을 둔다.
- 상태: 사용자별 변경 상태를 DB에 저장하며 브라우저 저장소를 정본으로 사용하지 않음

## 운영 전 남은 일

- 심사용 예시 데이터를 검수된 실데이터로 교체한다.
- JSONB 데이터셋 중 관리 화면에서 자주 수정하거나 관계 무결성이 중요한 영역은 정규화된
  도메인 테이블로 단계적으로 분리한다.
- 쓰기 기능별 감사 이벤트와 충돌 제어를 확대하고 RLS·API 권한 회귀 테스트를 보강한다.
- 운영 배포에서는 심사용 계정 표시와 심사용 추천·매칭 데이터를 비활성화한다.

## 품질 게이트

각 단계는 다음 항목을 모두 통과해야 완료로 본다.

- 마이그레이션을 빈 DB와 기존 DB에 각각 적용할 수 있다.
- API의 미인증·권한 부족·잘못된 입력·중복 요청을 테스트한다.
- 새로고침과 재로그인 후에도 저장 결과가 유지된다.
- 운영 빌드에서 `src/data` 직접 import와 silent fallback이 없다.
- `npm run lint`, `npx tsc --noEmit`, `npm test`, `npm run build`가 통과한다.

인증 환경과 최초 마이그레이션 실행 방법은
[`supabase-auth-setup.md`](./supabase-auth-setup.md)를 따른다.
