# 사람↔사람 매칭 트랙 — 지금 어디까지 왔고, 앞으로 어떻게 가는가

이 문서는 `agent/matching-m0m1` 브랜치(19커밋)를 feature 브랜치에 붙일 때
리뷰어와 팀이 오해 없이 읽어야 할 상태 설명이다. 특히 한 가지를 앞에 박아둔다:

> **이 브랜치에는 임베딩이 없다.** 지금 돌아가는 추천은 규칙 기반 엔진이고,
> 이 브랜치가 한 일은 "임베딩을 나중에 합법적으로, 풍부하게 적립할 수 있는
> 데이터·동의·프라이버시 기반을 까는 것"까지다.

## 1. 지금 사이트에서 보이는 것

demo 모드(`npm run dev:demo`, :3005)에서 온보딩을 완료하면 추천이 즉시 바뀐다.
이것은 임베딩 유사도가 아니라 **규칙 엔진**의 산출이다: 내 수요 태그와 상대
공급 태그의 교차(정방향×역방향 상호이익 결합), 지역·분야·미션 어휘·조직
협력관계 그래프의 공통축 보정, 그리고 동의·거절·수용량·필수제약을 먼저 걸러내는
하드필터. 점수 화면(/admin/rules)에서 가중치를 바꾸면 서버가 재산출한다.

추천 상세의 "왜 이 연결인가" 4문장은 LLM 창작이 아니라 점수 계산에 실제로 쓰인
데이터 포인터로만 조립된다. 근거 없는 문장은 만들지 않는 것이 이 트랙의 원칙이다
(뷰어 데모에서 "근거를 조립하지 못한 pair는 추천에 올리지 않는다"로 확정된 것과
같은 원칙).

## 2. 이 브랜치가 실제로 만든 것 — 세 층

**데이터 계약(M0).** 회원 8명의 목업 프로필을 Need/Offer/ImpactIntent/Consent
아이템 단위로 분해했다. "한 사람 = 벡터 하나"가 아니라 "한 사람 = 근거 있는
아이템 여러 개"가 되도록 — 임베딩도 아이템 단위로 적립하기 위한 구조다.
용어(사회혁신활동가/지원가 등)는 versioned vocabulary로 관리해 라벨이 바뀌어도
이력이 남는다.

**규칙 매칭 기준선(M1).** 위 아이템을 소비하는 상호(reciprocal) 매칭 엔진과
평가 하니스. 임베딩이 들어오면 이 기준선과 shadow 비교해 "임베딩이 정말 더
나은가"를 수치로 판정한다(M2). 기준선 없이 임베딩부터 넣으면 좋아졌는지
알 수 없기 때문에 이 순서를 택했다.

**프라이버시·동의 경계(C1~C5 + P1-1).** 다섯 번의 상호 리뷰를 거쳐 확정된
부분이자 이 브랜치의 가장 큰 부피다:

- 비공개 원문(수요 인용문, 동의 레코드, 점수 시드)은 서버에서만 읽힌다.
  클라이언트 번들에 원문이 실리는지 빌드마다 스캔하는 게이트가 CI에 있다.
- 매칭에 쓰이는 텍스트는 **사용자가 온보딩 마지막 화면에서 직접 승인한
  문구(safe_match_text)뿐**이다. 승인 영수증은 서버가 동의를 확인하고
  발급하며(위조 참조는 엔진이 차단), 미승인 문구는 태그로만 매칭에 참여한다.
- 동의는 목적별 3분리(공개노출/매칭사용/원문인용)이고 기본값은 전부
  꺼짐(opt-in)이다. 거절한 추천은 다시 노출되지 않고, 모듬(그룹) 추천은
  참여자 전원 동의 없이는 나가지 않는다.

이 층이 먼저 있어야 하는 이유: 임베딩은 만들기는 쉽지만 지우기는 어렵다.
"무엇을 임베딩해도 되는가"를 코드로 강제해두지 않으면, 나중에 동의 철회·원문
유출 문제를 임베딩 저장소에서 역추적해야 한다. 지금 구조에서는 임베딩 입력
자격(승인 문구 + 영수증 + 동의 purpose)이 데이터 계약에 걸려 있어서, M2는
"자격 있는 텍스트를 벡터로 바꾸는 일"만 하면 된다.

## 3. 아직 아닌 것 — 정직한 목록

- **임베딩 없음.** KURE-v1 실험은 사혁넷 공개 블로그 522글로 로컬 데모
  뷰어에서만 검증했다(파이프라인 무결성·투영 왜곡 정량 분석 완료). repo 앱과는
  분리돼 있고, 통합 방식은 별도 결정문(2026-07-29-demo-viewer-integration-plan)
  대로 server-gated `/labs/people-matching`으로 간다.
- **영속화 없음.** 온보딩 입력은 브라우저 세션에만 남는다(새로고침 시 소실).
  Supabase `nvc_` 테이블·RLS·pgvector는 DDL 초안만 있고 실행은 사용자 승인
  게이트(M4)다.
- **블로그 증거 미연결.** 522글에서 추출한 mention 3,448·claim 1,976·연결후보
  176건은 전부 `proposed`/`needs_review` 상태다. 본인이 "이 글이 나를 다룬 글"
  이라고 확인(user_claimed_subject)하기 전에는 매칭·임베딩에 쓰지 않는다는
  원칙이 걸려 있고, 그 확인 UI가 아직 없다.
- **온보딩 나머지 갭 미착수.** 필수제약(Constraint)·수용량(capacity)·역할
  자기선언(RoleAssertion)·동의 철회 cascade는 Codex와 스코프 합의까지 끝났고
  구현은 중단 지시에 따라 시작하지 않았다.

## 4. 향후 진행 순서 (합의된 로드맵)

1. **통합.** Codex 독립 재검토 → `agent/matching-m0m1` → feature 병합(저자
   보존) → origin/main `08eec42`(용어 치환) merge + vocabulary resolver 후속
   (별도 결정문 2026-07-29-main-08eec42-integration-plan 순서 그대로).
2. **M2 — 임베딩 shadow.** 승인 문구·공개 프로필로 MatchDocument를 만들고
   KURE-v1(한국어 1차) + BGE-M3(baseline) 임베딩을 아이템 단위로 생성.
   규칙 엔진 기준선과 같은 평가 하니스에서 shadow 비교 — 추천 품질이 수치로
   나아질 때만 노출 경로에 올린다.
3. **온보딩 확장 (합의 스코프 P1-2~).** 필수제약·수용량 수집(엔진 소비처와
   동시 구현), "이 글이 본인을 다룬 글인가요?" 확인 스텝(확인=주장 단계이지
   증명이 아니며, 개별 경험 승인과 분리), 역할 자기선언(복수 역할 + 이력 보존),
   동의 철회 시 영수증 무효화→벡터·인덱스·캐시 삭제까지 fail-closed E2E.
   이게 붙으면 "개인 데이터가 풍부해지는" 실제 레버(블로그 claim 1,976건)가
   프로필로 들어오기 시작한다.
4. **M4 — 영속화 (사용자 승인 게이트).** Supabase `nvc_` 스키마 실행,
   세션 적립분의 DB 이전, 실인증 결속(지금은 mock auth라 personaId가
   클라이언트 신고값이라는 한계가 문서화돼 있다), pgvector로 임베딩 저장.
5. **데모 뷰어 통합.** 별도 브랜치 `agent/demo-viewer-integration`에서
   server-gated 라우트로. 1MiB HTML을 public에 넣지 않는다.

## 5. PR 본문에 쓸 요약 (복붙용)

> 사람↔사람 추천의 기반 3층을 넣는 PR입니다: ① 아이템 단위 개인 데이터
> 계약(M0) ② 상호이익 규칙 매칭 기준선 + 평가 하니스(M1) ③ 서버 경계
> 프라이버시·동의 체계(원문 클라 번들 0건 게이트, 사용자 승인 매칭 문구,
> opt-in 동의, 거절 재노출 차단, 그룹 전원동의). **임베딩은 이 PR에 없으며**,
> 여기서 깐 승인·동의 계약이 M2 임베딩의 입력 자격을 규정합니다. 온보딩
> 입력은 아직 세션 영속(DB는 M4 승인 게이트). 검증: vitest 161/161,
